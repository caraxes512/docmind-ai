# Deployment Guide

## Local development

```bash
cp .env.example .env              # fill in JWT_SECRET_KEY, ENCRYPTION_KEY, OPENAI_API_KEY at minimum
docker compose up --build
```

`docker-compose.override.yml` is picked up automatically — it exposes Postgres/Redis/Qdrant ports to
the host and mounts `backend/app` for hot-reload. **Never carry that file's contents into a real
deployment** (see its own header comment).

First run: the backend's entrypoint (`backend/docker/entrypoint.sh`) waits for Postgres, then runs
`alembic upgrade head` automatically. If this is a genuinely fresh database with no migrations yet
generated (this project's migrations were never generated against a real Postgres instance — see the
note in every Step 2-9 summary about sandbox network restrictions), generate the initial one first:

```bash
docker compose run --rm backend-api alembic revision --autogenerate -m "initial schema"
docker compose run --rm backend-api alembic upgrade head
```

Review the autogenerated migration before applying it in anything beyond local dev — autogenerate is a
strong starting point, not a substitute for reading the diff.

- Frontend: http://localhost:3000
- Backend API docs: http://localhost:8000/docs
- Backend health check: http://localhost:8000/api/v1/health

## Required environment variables

See `.env.example` (compose-level), `backend/.env.example`, and `frontend/.env.local.example` for the
full list. The ones that gate startup or core functionality:

| Variable | Required for | Notes |
|---|---|---|
| `JWT_SECRET_KEY` | Everything | `docker-compose.yml` refuses to start without it set at all; `ENVIRONMENT=production` additionally refuses the placeholder default |
| `ENCRYPTION_KEY` | GitHub token storage | Same enforcement as above. Must be a 32-byte url-safe base64 Fernet key |
| `OPENAI_API_KEY` | Any AI feature | Required at startup when `ENVIRONMENT=production` |
| `GITHUB_CLIENT_ID` / `GITHUB_CLIENT_SECRET` | GitHub OAuth login, private repo cloning | App works without these; those two features just won't |
| `STORAGE_BACKEND` | File storage | `local` (default, disk-backed) or `s3` — see below |

## File storage: local vs. S3

`STORAGE_BACKEND=local` writes to `LOCAL_STORAGE_ROOT` inside the container, backed by the
`backend_storage` named volume in compose. This works for a single-instance deployment but:

- Doesn't survive volume loss without your own backup strategy
- Doesn't work at all if you ever run more than one `backend-api`/`celery-worker` replica (each would
  see a different local disk)
- Has no pre-signed download URL support — `ExportService.get_download` will fail (see
  `LocalFileStorage.get_download_url`'s docstring)

**Any deployment beyond a single local instance should use `STORAGE_BACKEND=s3`.** Required IAM
permissions for the bucket: `s3:PutObject`, `s3:GetObject`, `s3:DeleteObject`, `s3:ListBucket`. The app
authenticates via the standard AWS credential chain (environment variables, an instance/task role, or
`~/.aws/credentials` — whatever `aioboto3`'s underlying `botocore` picks up; no credentials are
hardcoded or passed through app settings).

## Database migrations

Alembic is wired (`backend/alembic.ini`, `backend/app/db/migrations/env.py`) and runs automatically on
container start via the entrypoint script. For manual migration work:

```bash
docker compose run --rm backend-api alembic revision --autogenerate -m "describe the change"
docker compose run --rm backend-api alembic upgrade head
docker compose run --rm backend-api alembic downgrade -1   # roll back one revision
```

## Deploying

This repo ships container images (`.github/workflows/deploy.yml` builds and pushes to GHCR on merge to
`main` and on `v*` tags) but deliberately does **not** wire a specific deploy target — "deploy" means
meaningfully different things depending on where you're running this, and picking one in the CI
workflow would make the guidance below misleading for everyone not using that target. Options, roughly
in order of operational simplicity:

1. **Single VM + docker-compose** — pull the images, run `docker compose -f docker-compose.yml up -d`
   (note: base file only, not the dev override) on a VM with the env vars set. Simplest to reason
   about; you own patching/scaling/backups.
2. **Managed container platforms** (Fly.io, Render, Railway) — point them at the pushed images or let
   them build from the Dockerfiles directly; they handle TLS, restarts, and basic scaling for you.
3. **Cloud-native** (ECS Fargate, Cloud Run, AKS) — most operational leverage, most setup: you'll need
   your own Postgres (RDS/Cloud SQL), Redis (ElastiCache/Memorystore), and a Qdrant deployment (their
   managed Cloud offering, or self-hosted), plus secrets management (Secrets Manager/Secret Manager)
   instead of a `.env` file.

Whichever you choose: run `backend-api`, `celery-worker`, and `frontend` as separate scalable units
(they already are, in compose) — the worker is the one that benefits most from horizontal scaling under
load, since documentation generation and repository ingestion are the slow, LLM-bound operations.

## Observability

- Structured JSON request logs ship from `RequestLoggingMiddleware` (Step 5) — pipe container stdout to
  whatever log aggregation your platform provides (CloudWatch, Loki, etc.); no code change needed.
- `LLMUsageLog` rows (Step 7) give you a cost-per-agent breakdown queryable directly from Postgres —
  worth a scheduled export/dashboard once usage is non-trivial.
- The `/api/v1/health` endpoint is liveness-only (process is up), not readiness (DB/Redis/Qdrant
  reachable) — see that endpoint's docstring for why, and add a `/health/ready` variant if you put this
  behind a load balancer that should stop routing to an instance with a dead DB connection.

## What's genuinely unverified in this project

Stated plainly, consistent with every step's summary: this entire project was built in a sandboxed
environment with no network access, so no dependency was ever actually `pip install`ed or `npm
install`ed, no migration was ever run against a real Postgres instance, and no request ever hit a real
FastAPI server. Verification throughout relied on: syntax checking every file, hand-tracing logic
carefully, and — for the pure-logic pieces with no heavy external dependency (parsers, chunking,
security-critical zip extraction, agent retry/validation logic) — actually executing the real code via
`sys.modules` stubbing techniques, documented per-step. Tree-sitter grammar parsing, Qdrant vector
search, and the full FastAPI/SQLAlchemy stack were written carefully against documented APIs but never
executed. **Before trusting this in production, run the full test suite for real** (`pytest`, all
markers, `-m integration` included) against real infrastructure, and treat any failure as expected
first-run friction to fix, not a sign the approach was wrong.
